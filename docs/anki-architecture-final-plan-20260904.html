结论先行；证据与细节折叠。目标不是“拆更多文件”，而是让插件沿 Anki 官方提供的运行方式工作。

插件的 Python module、hooks、配置、HTML 界面都符合 Anki 插件模型；偏离主要发生在自建 HTTP 服务器、主线程同步查询、AnkiConnect 兼容层、私有 backend/protobuf。

02 · important correction

线程模型需要修正：不是“Collection 只能在主线程”

当前方式
HTTP 请求线程
↓ run_on_main()
Anki UI 主线程
卡片查询 · SQL · FSRS
↓ Event.set()
请求线程苏醒并继续

安全地避开了并发乱访问，但长查询会冻结 UI；请求线程还用 Event 同步等待最多 120 秒。

官方推荐方向
Anki UI 主线程
只负责发起与接收结果
↓ 启动 QueryOp
后台操作
只读 Collection 查询 + 分析计算
↓ success callback
UI 主线程更新页面

只读/不可撤销的长操作用 QueryOp；UI 更新回主线程。Collection 操作默认串行，避免与写操作交错。

因此：mw.taskman.run_on_main() 不是错的能力，但这里用错了方向。它更适合后台任务偶尔更新 UI；本插件却用它执行整批 collection 查询。

界面

QDialog 内嵌 AnkiWebView；JS 用 bridge 请求刷新，Python 回传 JSON。

后台

一次 QueryOp 读取数据并完成分析，避免多轮线程切换与并发刷新。

兼容性

FSRS 私有调用若暂时无公开替代，只允许存在于一个 adapter，并配版本门槛。

如果“必须在系统浏览器独立打开”是产品要求，可继续保留 localhost server；但那时应增加随机访问令牌、single-flight、防并发刷新和清晰生命周期。当前没有这个硬要求，所以首选 WebView。
04 · things easy to miss

额外发现：你前面没有问到，但值得纳入

私有 backend 与 protobuf 是最大的升级风险
collection._backend.simulate_fsrs_review() 直接碰以下划线标记的私有对象；当前 Anki 源码明确警告 backend 方法可随时变化，应通过 Collection 的公开方法。Anki 架构文档也说明 protobuf 不是公共接口。本插件还直接导入 SimulateFsrsReviewRequest。如果当前没有公开的等价方法，正确策略是集中隔离 + 明确兼容版本 + 失败降级，而不是让私有类型扩散。
本地 HTTP 接口虽然只绑 127.0.0.1，仍有隐私与并发成本
接口无需认证即可返回牌组名、卡片正面、标签和复习行为。远程机器通常访问不到，但本机其他进程可以读取；未来若增加写操作，风险会更高。ThreadingHTTPServer 还会为并发请求创建处理线程，多次刷新可能同时跑多份昂贵计算。
profile 切换/关闭时存在生命周期竞态
profile_will_close 异步关闭服务器并立即清空全局变量；此时已在处理的请求仍可能接触即将关闭的 collection，新一次启动也可能撞上尚未释放的端口。内嵌窗口跟随 profile 生命周期会简单很多。
直接 SQL 读取 revlog：只读不等于稳定
官方文档允许 DB 查询，但建议尽量使用 Collection 方法；当前 Anki 已有公开 get_review_logs(card_id)。逐卡调用可能有性能代价，因此计划不是盲目替换，而是先基准比较：若保留批量 SQL，必须藏在数据 adapter 内并有字段契约测试。
测试绕开插件包，说明真正的运行 interface 没被测试
测试通过 spec_from_file_location() 单独加载一个文件，因为正常 import 依赖 aqt 并触发副作用。这不是测试技巧问题，而是纯计算、Anki adapter 和 UI 注册尚未分开。
manifest 缺少兼容性声明与发布版本信息
目前只有 name/package。项目使用 QueryOp、FSRS 与私有 backend，必须选定并验证最低 Anki 版本，然后补 min_point_version、human_version 等信息；私有 FSRS 适配还应在最低版和最新稳定版做烟雾测试。
